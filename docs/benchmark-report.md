# LinkStamp 同机热点压测报告

## 1. 测试方法与环境

2026-11-22，在一台 Windows 11 主机（32 个逻辑 CPU，约 32 GiB 内存）上运行跳转服务、MySQL、Redis 与发压器。比较统计优化前的 [`893def5`](https://github.com/QYL66/linkstamp/tree/893def5) 与 [`f697dfb`](https://github.com/QYL66/linkstamp/tree/f697dfb)。两版用同一份含历史访问的测试快照，按版本恢复，给新版应用访客/IP 联合索引迁移。Redis 也从快照恢复缓存和消费组，使用 AOF everysec。被测跳转缓存为热态，统计一直开启，匿名跳转限流只在隔离测试实例关闭。每轮排空后静置 12 秒再开下一轮。

- **发压**。Apache JMeter 5.6.3、Java 17、CLI 非 GUI 模式，使用 [Open Model Thread Group](https://jmeter.apache.org/usermanual/component_reference.html#Open_Model_Thread_Group)。开放式的到达计划独立于上一请求是否结束，可减少服务变慢时发压随之放缓造成的协同遗漏。每轮从 5 RPS 爬坡 15 秒，接着按目标速率运行 60 秒，随后留 8 秒让在途 HTTP 请求结束。配对种子为 `1001 / 2002 / 3003`。
- **流量**。100 条活跃短链生成 1,000 行共享 CSV，20 条热点各出现 40 次，80 条长尾共出现 200 次，以种子 `802022` 洗牌并循环使用。每次到达只发一个 GET，校验 `302` 和完整 `Location`，不跟随跳转。
- **计量**。按请求开始时间取后 60 秒的 JTL 样本，计算实际到达速率、成功吞吐、错误率和成功跳转 P99。对账使用整轮 75 秒内开始且通过两个断言的请求，逐项比对访问明细、Stream ID 去重记录、日报 PV、累计 PV 增量。Redis 启动时确认目标消费组能读到数值 lag，稳态每 10 秒取样，停压附近加密采样。积压以该消费组的 `lag + pending` 为准。只有三轮停压均为 0 才记为“停压零积压”；停压有残留且 1 秒内消化的场次单记为瞬时在途。

达到任一红线即停止该版本升档，另一版按自己的结果继续。

1. 每 10 秒采样的积压连续三次严格上升，且停压积压超过该轮稳态成功数的 10%。
2. 停压后 30 秒仍未排空。
3. 稳态错误率超过 0.5%，或成功跳转 P99 超过 500 ms。
4. 任一项增量对账不一致。排空超时时保留截止时点与缺口，等待中的消息仍计入积压。

逐轮摘要保留实际到达速率与 JMeter 进程 CPU 峰值（100% 为占满一个逻辑核）；偏离目标超过 `max(目标速率 × 12%, 1 RPS)` 的轮次另行标记。复现可用 [JMX 测试计划](benchmark/LinkStamp.jmx)、[CLI 属性](benchmark/cli.properties)、[热点 CSV 生成器](benchmark/make_hotspot.py) 和 [执行命令](benchmark.md#复现)。[全部 11 轮 JTL 摘要及 CPU 记录](benchmark/jmeter-summary.csv)。

## 3. 新版稳态容量边界

新版最高达标测试档为 **20 RPS**。三轮实际到达及成功吞吐均为 19.983 RPS、错误均为 0，停压积压分别为 61、28、10 条，分别在 4.496、1.903、0.620 s 排空，四项对账全部一致。

| 触线轮次 | 实际到达 / 成功吞吐 | 稳态成功 / 错误 | 302 P99 | 停压积压 | 排空与对账 |
| --- | ---: | ---: | ---: | ---: | --- |
| `893def5`，20 RPS / 1001 | 19.983 / 19.983 RPS | 1,199 / 0 | 108 ms | 626 条 | 截止 30 s 仍有 241 条在途；整轮成功 1,387，四项统计各录得 1,157 |
| `f697dfb`，40 RPS / 1001 | 39.867 / 39.867 RPS | 2,392 / 0 | 87 ms | 541 条 | 11.702 s 排空，整轮成功和四项增量均为 2,737 |

新版 40 RPS 触发积压停止线，停压积压为稳态成功数的 **22.6%**。单轮触线后停止升档。下表是该轮目标采样时点附近的 Redis 读数，停压行取窗口结束后约 0.26 s 的独立样本。

该轮 JMeter CPU 峰值 316.8%（约 3.17 核），稳态实发达到目标的 99.7%。从本轮实际到达率看，没有出现发压器发不满的现象。同机的 CPU 峰值仍无法排除个别线程或其他共享资源的影响。20 RPS 是这套机型、数据、时间窗和停止准则下的最高达标档，20–40 RPS 之间尚未细测。

## 4. 40 RPS 瓶颈诊断与下一步

跳转成功数接近计划到达数，跳转 P99 和错误率未越线，同时消费组多次累积未读事件，停压后逐步排空并完成对账。优先排查异步消费阶段。新版读完一批后接着拉取下一批，降低批间等待。每次仍逐条持有短链写锁、登记 Stream ID、写多张统计表、提交事务并 ACK。[`f697dfb` 消费实现](https://github.com/QYL66/linkstamp/blob/f697dfb/project/src/main/java/io/github/qyl66/linkstamp/project/mq/consumer/ShortLinkStatsSaveConsumer.java)。

| 待验证因素 | 验证与改造 |
| --- | --- |
| 共机 MySQL 的事务提交、日志刷盘与单条多表写入 | 同时采集事务和 I/O 等待、redo fsync、批内单条处理阶段耗时。对照试验在批内按维度预聚合 PV，批量写访问明细和去重记录，保留一个可回滚的事务边界及提交后 ACK。 |
| 热点短链的写锁与未来并行消费者的竞争 | 采集锁等待和持锁耗时，分别测 80/20 与均匀流量，再加迁移场景。验证消费读锁、迁移写锁的分离方案，并通过按短链串行化或原子去重守住 UV/UIP 与迁移一致性。 |

本次未采集 SQL、刷盘和锁等待的分段计时，因此没有给它们排序或估算各自占比。在同样快照和对账要求下补测 20–40 RPS 拐点，再逐档扩展。后续目标为 **200+ RPS** 稳态通过，须以上述红线、三轮复验与四项对账验收。
