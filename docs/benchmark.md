# LinkStamp 短链跳转与访问统计压测

用 Apache JMeter 5.6.3、Java 17 和开放式线程组比较 \`893def5` 与 `f697dfb`。前者为统计优化前版本，后者让消费者连续拉取批次，并改用联合索引做访客和 IP 存在性查询。被测接口为本机缓存热态下的短链 GET，统计链路始终开启。

## 对照条件

- JMeter 及服务同机运行。使用独立 MySQL、Redis 和应用实例，使用相同的 JVM 参数与统计配置。匿名跳转限流只在隔离环境关闭。Redis 两版均使用 AOF everysec。
- 用同一份包含 100 条短链和历史访问明细的数据库数据快照。新版恢复后应用访客/IP 联合索引迁移。分发完全相同的短链列表。Redis 从同一快照恢复消费组和跳转缓存，启动后核对 lag、pending 与各计数。
- 热点 CSV 共 1,000 行。20 条热门链各出现 40 次，80 条长尾共出现 200 次，使用固定洗牌种子 `802022`。开始前核对列表和目标。单次访问校验 `302` 和完整 `Location`，关闭重定向跟随。
- 旧版和新版每个配对档按 `1001`、`2002`、`3003` 重复。每轮先爬坡 15 秒，再按目标到达速率持续 60 秒，留 8 秒让在途 HTTP 请求收尾。下一轮在确认排空后额外静置 12 秒。

## 指标与停止条件

- 吞吐、错误率和 P99 依据 `.jtl` 的请求开始时间截取 60 秒稳态窗口。整体对账收录预热和稳态中 HTTP 302、Location 均通过断言的请求。
- Redis 取同一消费组的 `lag + pending`。每 10 秒观察趋势，停压附近高频采样，再观察排空。停压有残留且在 1 秒内清空时，记录为瞬时在途量。只有三个种子在停压采样均为 0，才注明该档停压零积压。
- 连续三个积压采样递增且停压积压超过稳态成功数的 10%、30 秒内未排空、响应错误率超过 0.5%、P99 大于 500 ms、任意一项统计增量对账失败，均停止该版本升档。30 秒时未排空的对账仍在进行，不能作为消息遗失证据。
- 对账分别计算访问明细、Stream 去重记录、日报 PV、累计 PV 的增量。四项均须等于整轮成功跳转数。发压端资源和实际速率同时保留，凡无法达到目标发压窗口的场次单独标记。

## 复现

使用 [JMeter 测试计划](benchmark/LinkStamp.jmx) 和 [热点样本生成器](benchmark/make_hotspot.py)。文件 `paths.txt` 每行一个独立测试环境里的短链路径。目标应用运行在本机 `38003`。每次换版本前恢复相同的数据快照，再用该版本复验。同版本每轮排空后静置 12 秒。

```powershell
python docs/benchmark/make_hotspot.py paths.txt urls_hotspot_80_20.csv
$env:HEAP = '-Xms128m -Xmx512m'
jmeter -n -q docs/benchmark/cli.properties -t docs/benchmark/LinkStamp.jmx -Jlinks=D:/path/to/urls_hotspot_80_20.csv -Jrate=20 -Jwarmup=15 -Jduration=60 -Jseed=1001 -Lorg.apache.jmeter.threads.JMeterThread=WARN -l r20-1001.jtl -j r20-1001-jmeter.log
```

[逐轮 JMeter 摘要](benchmark/jmeter-summary.csv)

表中延迟、积压和排空均为同档三轮中位数。未完成三轮的失败档见逐轮摘要。

| 版本 | 目标 RPS | 实际成功 RPS | P99（ms） | 停压积压 | 排空（s） | 四项对账 |

- `893def5` 最高达标档为 10 RPS，下一失败档为 20 RPS。达标档和生产容量在不同负载、硬件与时长下需重新验证。
- `f697dfb` 最高达标档为 20 RPS，下一失败档为 40 RPS。达标档和生产容量在不同负载、硬件与时长下需重新验证。

触线场次保留在 CSV 中。排空超时后采到的是截止时的阶段统计。
